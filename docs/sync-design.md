# Aoide curation store — local schema and sync contract

Melete owns the library. This owns everything about how it is listened to.

The split is deliberate and worth stating precisely, because every design decision
below follows from it:

- **Melete remains source of truth for** files, tags, artwork, item identity, and
  which music exists at all.
- **The curation store is source of truth for** playlists, folders, likes, play
  history, queue state, and smart-playlist rules.

Nothing here duplicates what the server does. The store began beside Jellyfin,
whose music model was an afterthought on a video server (play counts that moved at
playback *start*, albums with no play statistics), and the Aoide sidecar plugin
synced it. Melete, which replaced both, keeps this design: it serves the same
routes and stores the same op log, so the clients did not change shape.

The field is still called `jellyfin_id` (`jellyfinId` in the app's tables)
everywhere below, because the name is part of the wire format every device and
Melete share. It holds a Melete track id now; entries written before Melete hold
Jellyfin's hex ids.

## Principles

1. **Local-first.** Every read and write hits SQLite. The network is never in the
   path of a user action. Offline is not a degraded mode; it is the normal mode that
   sometimes also syncs.
2. **Sync operations, not state.** An append-only op log, not a diff of two
   snapshots. Two devices that edit different fields of the same playlist must both
   win, and state-sync cannot express that.
3. **Every op is idempotent.** Client-generated UUID per op; applying it twice is a
   no-op. This is what makes retry-on-failure safe, which is what makes the sync
   engine simple enough to trust.
4. **Soft deletes only.** A hard delete cannot be synced — the absence of a row is
   indistinguishable from never having seen it.

## The identity problem

**This is the highest-risk part of the whole design.** Everything below stores
references to the server's track ids, and those ids are less stable than they look:
they belong to a file (a library and its path in it), so moving files or re-adding a
library mints new ones on the next scan. Every playlist entry and history row would then dangle silently — the
playlist still lists ten songs, and none of them resolve.

So every reference is stored **twice**:

- `jellyfin_id` — the fast path, used for every normal lookup.
- `content_key` — a fingerprint that survives a rescan, used to relink when the id
  stops resolving.

```
content_key = sha256(lower(trim(artist)) | lower(trim(album)) | lower(trim(title)) | round(duration_seconds))
```

`musicbrainz_id` is stored alongside when the files carry the tag, and takes
precedence over `content_key` when present — it is a real identifier rather than a
heuristic.

Relinking runs when a lookup by `jellyfin_id` misses: search by `musicbrainz_id`,
then by `content_key`, and rewrite the stored id on a hit. A track that matches
neither is marked unresolved rather than deleted — the file may simply be offline,
and destroying a playlist entry because a drive was unmounted is unrecoverable.

## Schema

Every syncable table carries the same four columns:

| column | meaning |
| --- | --- |
| `id` | UUID, generated by whichever client created the row |
| `updated_at` | milliseconds since epoch, from the writing device's clock |
| `deleted` | soft-delete flag; rows are never removed |
| `origin_device` | which device wrote this version, used as the tiebreak below |

### `tracks` — local cache, **not synced**

Each device rebuilds this from its own connection to Melete, so it never travels.
Keeping it out of the sync payload is what keeps a full history sync small.

```sql
CREATE TABLE tracks (
  jellyfin_id     TEXT PRIMARY KEY,
  content_key     TEXT NOT NULL,
  musicbrainz_id  TEXT,
  title           TEXT NOT NULL,
  artist          TEXT NOT NULL,
  album           TEXT NOT NULL,
  album_artist    TEXT,
  duration_ms     INTEGER,
  year            INTEGER,
  genres          TEXT,              -- JSON array
  last_seen_at    INTEGER NOT NULL
);
CREATE INDEX idx_tracks_content_key ON tracks(content_key);
CREATE INDEX idx_tracks_mbid ON tracks(musicbrainz_id);
```

### `playlists`

```sql
CREATE TABLE playlists (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  description   TEXT,
  folder_id     TEXT,
  is_smart      INTEGER NOT NULL DEFAULT 0,
  smart_rules   TEXT,                -- JSON, see below; null unless is_smart
  sort_index    TEXT NOT NULL,       -- fractional index, see below
  updated_at    INTEGER NOT NULL,
  deleted       INTEGER NOT NULL DEFAULT 0,
  origin_device TEXT NOT NULL
);
```

### `playlist_items`

```sql
CREATE TABLE playlist_items (
  id            TEXT PRIMARY KEY,
  playlist_id   TEXT NOT NULL,
  jellyfin_id   TEXT NOT NULL,
  content_key   TEXT NOT NULL,
  position      TEXT NOT NULL,       -- fractional index
  updated_at    INTEGER NOT NULL,
  deleted       INTEGER NOT NULL DEFAULT 0,
  origin_device TEXT NOT NULL
);
CREATE INDEX idx_items_playlist ON playlist_items(playlist_id, position);
```

**`position` is a fractional index, not an integer.** This is not a detail. With
integer positions, inserting a track at row 3 renumbers every row below it, so two
devices inserting concurrently produce dozens of conflicting updates and a
last-writer-wins merge silently drops one of the inserts. A fractional index — a
sortable string, midpoint between its neighbours — means an insert writes exactly
**one** row and two concurrent inserts at the same spot both survive, merely in an
arbitrary relative order. Collaborative playlists work without any conflict
resolution at all.

### `folders`

```sql
CREATE TABLE folders (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  parent_id     TEXT,
  sort_index    TEXT NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted       INTEGER NOT NULL DEFAULT 0,
  origin_device TEXT NOT NULL
);
```

### `likes`

Owned here, and synced like everything else; Melete reads them out of the log
(`/api/v1/music/likes`) so other clients see them too. Local
ownership is what makes liking a song on a plane work; the log is what stops this
becoming a private silo.

```sql
CREATE TABLE likes (
  id            TEXT PRIMARY KEY,
  jellyfin_id   TEXT NOT NULL,
  content_key   TEXT NOT NULL,
  liked         INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted       INTEGER NOT NULL DEFAULT 0,
  origin_device TEXT NOT NULL
);
CREATE UNIQUE INDEX idx_likes_item ON likes(jellyfin_id);
```

### `album_likes`

An album's like: the same row and merge as a song's, naming the album by
`album_id` in place of `jellyfin_id`, with the content key `artist|album`.
Its own entity rather than a kind of song like, so a build that predates it sets
the row aside (quarantine) instead of reading it as a song's. Liking an album
likes none of its songs. The app writes these through Melete
(`PUT`/`DELETE /api/v1/music/albums/{id}/like`), which appends the op, and only
ever pulls them; so nothing is held back for a server without them.

```sql
CREATE TABLE album_likes (
  id            TEXT PRIMARY KEY,
  album_id      TEXT NOT NULL UNIQUE,
  content_key   TEXT NOT NULL,
  liked         INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted       INTEGER NOT NULL DEFAULT 0,
  origin_device TEXT NOT NULL
);
```

### `play_events` — append-only

The raw material for real play counts, recaps, weighted shuffle and skip tracking.
Never edited after insert, which makes it the easiest thing in the system to sync:
there is no such thing as a conflicting append.

```sql
CREATE TABLE play_events (
  id            TEXT PRIMARY KEY,
  jellyfin_id   TEXT NOT NULL,
  content_key   TEXT NOT NULL,
  started_at    INTEGER NOT NULL,
  ended_at      INTEGER,
  ms_played     INTEGER NOT NULL,
  completed     INTEGER NOT NULL DEFAULT 0,
  skipped       INTEGER NOT NULL DEFAULT 0,
  source        TEXT,                -- album | playlist | shuffle | search | siri | carplay
  origin_device TEXT NOT NULL
);
CREATE INDEX idx_events_track ON play_events(jellyfin_id);
CREATE INDEX idx_events_time ON play_events(started_at);
```

Note what this buys that a server-side play count cannot give: a *play* is defined
here, not by the server. "Completed" means the track actually finished; a skip at four
seconds is recorded as a skip rather than as a play. A count taken at the moment
playback starts treats both identically; Melete instead reads these events into its
own play history, with how each one ended.

### `queue_state`

One row per device. "Resume across devices" reads the most recently updated row
belonging to a *different* device.

```sql
CREATE TABLE queue_state (
  device_id     TEXT PRIMARY KEY,
  device_name   TEXT NOT NULL,
  track_ids     TEXT NOT NULL,       -- JSON array of track ids
  position      INTEGER NOT NULL,
  elapsed_ms    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  origin_device TEXT NOT NULL
);
```

### `ops` — the outbound log

```sql
CREATE TABLE ops (
  op_id       TEXT PRIMARY KEY,      -- UUID, the idempotency key
  entity      TEXT NOT NULL,         -- table name
  entity_id   TEXT NOT NULL,
  operation   TEXT NOT NULL,         -- upsert | delete
  payload     TEXT NOT NULL,         -- JSON of the full row after the change
  created_at  INTEGER NOT NULL,
  synced      INTEGER NOT NULL DEFAULT 0
);
```

Every local mutation writes its table **and** appends here, in one transaction.
Either both happen or neither does; a row that changed without an op is a change
that silently never syncs.

### `sync_state`

```sql
CREATE TABLE sync_state (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- 'device_id', 'server_cursor'
```

## Smart playlist rules

JSON in `playlists.smart_rules`. Evaluated locally against SQLite, so a smart
playlist works offline and updates the instant a play event lands.

```json
{
  "match": "all",
  "rules": [
    { "field": "genre",       "op": "is",     "value": "Jazz" },
    { "field": "play_count",  "op": ">=",     "value": 3 },
    { "field": "last_played", "op": "before", "value": "-30d" }
  ],
  "sort":  { "field": "last_played", "dir": "desc" },
  "limit": 100
}
```

Fields resolve against `tracks` joined with aggregates over `play_events`. Relative
dates (`-30d`) are stored relative and resolved at evaluation time — storing an
absolute date would freeze "not played in a month" to one particular month.

## Sync contract

This is the part Melete implements (the sidecar did, before it). Two endpoints.

### Auth

```
Authorization: Bearer <the user's Melete token>
```

The sync routes are signed in like every other Melete route. **There is no separate
account for sync** — a second set of credentials would mean every friend has two
logins.

### `POST /aoide/sync/push`

```json
{
  "deviceId": "…",
  "ops": [
    { "opId": "uuid", "entity": "playlists", "entityId": "uuid",
      "operation": "upsert", "payload": { … }, "createdAt": 1754500000000 }
  ]
}
```

```json
{ "accepted": ["uuid", …], "cursor": 12345 }
```

The server assigns a monotonically increasing `seq` to each accepted op. Re-pushing
an `opId` it has already seen is accepted and ignored — that is what makes a client
retry after a timeout safe, and a client *will* retry after a timeout.

### `GET /aoide/sync/pull?since=<cursor>&limit=500`

```json
{ "ops": [ … ], "cursor": 12400, "hasMore": true }
```

Ops come back in `seq` order. The client stores `cursor` only after applying the
whole batch, so an interrupted sync replays rather than skips.

**Push before pull.** The client's own ops come back with a sequence number, which
is how it learns they were durably accepted.

### Conflict resolution

Last-writer-wins on `updated_at`, with `origin_device` as a deterministic tiebreak
when two clocks agree. Which side wins is arbitrary; that every device independently
reaches the *same* answer is not — two devices resolving one conflict differently
diverge permanently, and nothing afterwards notices.

**Per field for `playlists` and `folders`, per row for everything else.** The
per-field stamps live in a `fieldUpdatedAt` map *inside* the payload, so this needed
no server change at all: Melete stores payloads verbatim and never parses them,
which is exactly the schema evolution that opacity was preserved for. A row without
the map falls back to its `updated_at` for every field, so ops already in the log and
devices on older builds keep working with no migration.

Nothing else needs it. `playlist_items` and `likes` have one mutable field each, so
per-row already *is* per-field. `play_events` is append-only and cannot conflict. And
`queue_state` is deliberately excluded: merging a queue field by field could pair one
device's playback position with another device's track list, a state that existed on
neither and describes nothing.

The motivating example above — renaming and reordering at once — turns out never to
reach this path. Order lives in `playlist_items.position` as a fractional index, so
concurrent reorders are separate rows and both survive already. The real case is
narrower: two devices editing the *name* and the *description* of the same row.

Clock skew is handled with the server's `receivedAt`, but **both** references have to
agree before a timestamp is disbelieved: the writer must be ahead of the server *and*
ahead of the receiving device's own clock. Testing against the server alone cannot
tell a fast client from a slow server, and a server on a NAS with no RTC is a
slow server — every device then looks "ahead", every inbound row is dragged below the
local copy, and every device rejects every other device's edits permanently and
silently.

## As built

The contract above was written before either side existed. Where the running system
differs, the running system is right.

- **Entity names are translated at the wire boundary.** The store's tables are
  singular camelCase because the record types are; the server's allow-list is plural
  snake_case (`playlists`, `playlist_items`, `folders`, `likes`, `album_likes`,
  `play_events`, `queue_state`, `track_flags`) and matched strictly. Rewriting stored `op` rows to spell it the
  server's way would be a schema migration in service of a formatting preference, and
  would still leave ops written by older builds spelling it the old way.
- **`rejected` exists**, and is not in the design above. A push returns per-op
  refusals alongside `accepted`; a refused op will never be accepted, so it is
  quarantined and never retried. Failing the whole batch instead would let one
  malformed op wedge the queue forever.
- **A 5xx has no place in the contract and needed one.** An unhandled server
  exception fails the whole request, so the client retried the same bytes forever and
  every innocent change queued behind one the server could not swallow — the same
  wedge `rejected` prevents, through a door the contract does not cover. A push that
  5xxs is now bisected to find the offending op, which is quarantined alone; halves
  that succeed are pushed on the way past. A fault that stops reproducing when an op
  is sent alone is treated as transient and blamed on nothing.
- **`since` is always sent**, as `0` on a device that has never synced, rather than
  omitted. Omitting it is defensible and also the client being clever at the server's
  expense.
- **Payload depth is bounded server-side**, not client-side. Foundation refuses an
  over-nested document before any per-element seam exists, so there is no client
  defence to write.

## Cover images

Bytes are **not** in the op log. Payloads cap at 256 KB and every device replays the
whole log, so images carried inside ops would make a full history sync grow without
bound — the one property the whole design rests on.

The playlist row carries `image_hash` and `image_mime`, a few dozen bytes travelling
through the ordinary log with no server change, because payloads are opaque. The
bytes move through their own endpoints, addressed by their own SHA-256:

```
PUT  /aoide/images/{sha256}   body = raw bytes, Content-Type: image/jpeg|png|webp
GET  /aoide/images/{sha256}
HEAD /aoide/images/{sha256}   a cheap "do I need to upload this?"
```

Content addressing earns three things: re-uploading is a no-op rather than a
conflict, two playlists sharing a cover store one copy, and clients cache forever —
bytes behind a hash cannot change, so there is no invalidation problem to have.

**One ordering rule, and everything depends on it: upload the blob before pushing the
op that names it.** An op naming a hash the server does not hold leaves every other
device with a playlist whose cover can never be fetched, and nothing afterwards
notices — the row is perfectly valid, the image simply is not there. The client keeps
an `imageBlob` table recording which blobs it holds and whether the server has them,
reads the hashes out of the pending ops themselves so an op and its blob requirement
cannot drift apart, and uploads before push.

A cover that will not upload does not fail the sync: everything else still pushes and
the op naming it waits. A playlist arriving without its picture a few minutes late is
much smaller than a device that stops syncing because one image would not go.

Inbound covers are fetched **lazily**, when something is about to draw one, never
during sync — a device joining an account would otherwise download every cover in the
library before it finished syncing, most of which it will never show.

## Playlists on the server

Melete has no playlists of its own to keep in step: `/api/v1/playlists` reads
Aoide's playlists straight out of the log. On Jellyfin the sidecar exported them,
one way only, as native Jellyfin playlists, so an edit could never come back round
as an inbound change; with one writer that problem is gone.

## Phasing

Ten of the fourteen features need no server at all. They are worth building first,
because single-device means no sync, and sync is where all the difficulty lives.

**Phase 1 — local only, no server:** real play counts and history, skip tracking,
true queue persistence, weighted shuffle, playlist editing, folders, smart playlists,
auto-updating mixes, wrapped-style recaps, taste-based recommendations.

**Phase 2 — needs the server:** resume across devices, per-device downloads with
shared state, shared and collaborative playlists, public playlists, scrobbling.

Phase 1 still writes the op log from day one. That is the whole point of designing
these together: phase 2 becomes a sync engine reading an op log that already exists
and is already correct, rather than a migration.
